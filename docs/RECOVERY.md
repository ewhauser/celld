# Local restart and recovery tests

Run `pnpm test:recovery` (equivalent to `pnpm tck --profile local --suite recovery`). No AWS account is required. These are celld lifecycle invariants, separate from the 63-case differential API corpus; the reference profile is rejected because it has no Docker lifecycle control.

| Case                      | Fault                                                                                                                            | Checks after restart                                                                                                                                          |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `recovery.graceful`       | Stop celld gracefully, confirm exit 0, start the same container                                                                  | Acknowledged KV and SQL state, deleted key remains absent, rolled-back changes remain absent                                                                  |
| `recovery.crash`          | SIGKILL, confirm exit 137, start the same container                                                                              | The same acknowledged-state invariants                                                                                                                        |
| `recovery.facets`         | Seed a Durable Object facet, stop celld gracefully, restart the same container                                                   | The facet's own KV and SQL state is intact after a new activation                                                                                             |
| `recovery.overdue-alarm`  | Set an alarm, SIGKILL before its deadline, leave celld down past the deadline, restart                                           | Persisted state and eventual alarm execution                                                                                                                  |
| `recovery.disk-loss`      | Arm an alarm, SIGKILL, remove the owned celld container and state volume, recreate an empty disk, restart against retained MinIO | KV, SQL, deletions, rollback state, and overdue alarm execution restored without the old local disk                                                           |
| `recovery.storage-outage` | Stop MinIO, attempt three distinct writes, cold-restart celld after restoring MinIO                                              | Acknowledged writes survive; uncertain writes are absent or complete; KV/SQL transactions never partially persist; post-recovery write survives another crash |

`recovery.facets` uses a Worker Loader binding to load a child bundle whose `Ledger` class becomes the facet. In v0.6.0 the facet keeps [its own SQLite database and replication stream](https://github.com/denoland/celld/releases/tag/v0.6.0); the case asserts the facet's KV value and SQL row after a restart that changes the root object's activation. It does not test eviction while the node stays up, nor facet behavior during a multi-node ownership move.

Each case uses a separate DO identity. Before injecting the fault, the driver verifies the acknowledged state. Restart and disk-loss cases additionally record a per-activation random token and require it to change after restart. The outage case records Docker lifecycle transitions and checks transaction histories across two cold restarts. An acknowledgment is a complete successful HTTP response; no in-flight write is assumed absent after a crash. SQL cursors are consumed before responding.

The alarm test proves the container is stopped before the five-second alarm deadline. If stopping takes too long, the test fails rather than silently testing a live alarm. It then waits 11 seconds, beyond the pinned celld default ten-second lease lifetime, before restarting. Polling is bounded and only retries pending alarm completion; ordinary state assertions and write operations do not retry. Reads after restart may activate the object, so this does not prove autonomous alarm discovery without application traffic or exactly-once delivery.

All cases except `recovery.disk-loss` retain both disks. `recovery.disk-loss` deletes only celld's run-owned state volume and retains MinIO's disk. Before removal, the driver requires a stopped celld container, the expected `/state` volume mount, and matching Compose project/service/volume ownership labels. It removes the container and volume without forcing volume deletion, recreates the container, and checks the fresh volume is empty before starting celld. It verifies MinIO's container identity and start time remain unchanged. The entire owned Compose project is removed afterward, including volumes. This establishes process restart and single-node local-disk-loss recovery against a surviving MinIO bucket. It does not establish simultaneous object-store loss, AWS host behavior, arbitrary network partitions, or multi-node failover. It does not qualify MinIO as production S3. The durability expectations follow [celld's published guarantees](https://celld.dev/docs/guarantees/).

## Evidence and failure handling

Each run saves fixture hashes, deployment metadata, raw HTTP and commands, before/stopped/started Docker inspections, disk-loss ownership and empty-volume evidence, case observations, logs, JSON results, and JUnit results. Each fault checks Docker's stopped status and exit code. The driver refreshes the public endpoint after start, then waits for readiness. Failed lifecycle cases stop subsequent scenarios, which remain explicit infrastructure errors, and cleanup still runs. Known-bug API waivers do not apply to recovery cases.

Use `--case recovery.disk-loss` with `--suite recovery` for a focused run. The suite has an eight-minute deadline and restart scenarios have two-minute deadlines and the outage scenario has a three-minute deadline. Readiness and alarm completion each have separate bounds. A kill is restricted to the run-owned celld service; Only the outage case stops and restarts the run-owned MinIO service; unrelated Docker projects are never targeted.

Live-store network faults, multi-node fencing/failover, and additional lifecycle scenarios now run in the separate multinode, fleet, resilience, and qualification suites. They use distinct fault controls and oracles; this single-node suite does not imply their coverage.

## Object-store outage

The outage case first acknowledges a baseline transaction spanning SQL and KV. It stops only the run-owned MinIO service and records Docker proof that the service is stopped. It submits three different transactions once each, recording full responses or transport errors. Every acknowledged write must survive; a failed or timed-out operation may be absent or fully committed. Exact comparisons reject partial transactions, duplicates, unexpected IDs, and corrupted values. Harness errors and malformed successful responses are not treated as uncertain writes.

The outage spans at least a lease lifetime. Before restoring MinIO, the harness records celld's process state: an exited process must have code 3; a still-running process is killed explicitly for a cold recovery check. Exit code 3 alone is not proof of a particular fencing cause; runtime logs are retained. MinIO is restarted and checked before the harness starts celld, acting as its supervisor. After checking recovered state, a fresh transaction must succeed and survive one more SIGKILL/restart. Previously observed state must also remain unchanged.

This case tests a complete MinIO service outage with both disks retained. It does not prove asymmetric partition handling, multi-node fencing, or recovery when both disks are lost. Known-bug waivers do not apply. The evidence includes `outage-write-outcomes.json`, `outage-recovered.json`, `outage-final.json`, stopped-store inspection, process lifecycle snapshots, HTTP traces, and runtime logs.
