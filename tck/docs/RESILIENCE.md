# Three-node resilience

Run `pnpm test:resilience` (`--profile local --suite resilience`). This creates three celld nodes with separate disks and MinIO, using fleet durability. It runs ten ordered stages against a single growing SQL/KV history. All TypeScript orchestration and fixtures use Effect v4 RC.

The first five stages repeat routing, owner failure, old-owner rejoin, storage partition fencing, and peer-backed write recovery from [FLEET.md](FLEET.md). Routing also writes through the third node. The remaining stages are:

| Stage                  | Required observation                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `paused-owner`         | Freeze the owner beyond its lease lifetime; another node acquires a newer epoch and writes. Resume the old process, observe fencing, then restart it and read the complete history through every node.                                                                                                                                                                                                          |
| `interrupted-writes`   | Start six distinct atomic SQL/KV transactions with delayed responses, observe at least one entering the delay, kill the owner, and retain every HTTP outcome. At least one response must be uncertain. Every acknowledged transaction must survive; uncertain transactions may be wholly present or wholly absent. Partial transactions, duplicates, unknown IDs, and loss of earlier acknowledged writes fail. |
| `simultaneous-restart` | Kill all three processes, retain all disks, restart them, and read every acknowledged transaction through every node.                                                                                                                                                                                                                                                                                           |
| `follower-loss`        | Observe an active ensemble with both followers, kill one, observe an ensemble with the remaining follower, then acknowledge a new write while the leader cannot reach MinIO. Kill the leader and recover the full history on the sole remaining node before rejoining the others.                                                                                                                               |
| `replica-disk-loss`    | Acknowledge a write with the owner disconnected from MinIO, kill all nodes, remove each verified owned state volume, and prove its replacement is empty before restarting. Record full recovery, explicit recovery refusal, or a matching declared-data-loss record. Silent missing acknowledged data fails.                                                                                                    |

All-copy disk loss exceeds the fleet durability guarantee. celld v0.5.0 can publish a `log/<leader>.e<epoch>.loss.json` record when no complete witness survives. A passing assertion of that behavior is **not** a durability pass: `replica-disk-loss.json` records the observed outcome, exact history, and loss records. Loss records must match the leader generation and log epoch used for the fault. Surviving transactions must still be atomic. Recovery may complete if data reached the bucket before destruction; the suite records that outcome without claiming deterministic data loss.

Before the follower-loss and replica-disk-loss faults, the suite restarts the owner with both peers already available to establish a fresh two-follower ensemble. In v0.5.0 an already healthy one-follower ensemble does not automatically expand; merely waiting after simultaneous restart is insufficient. The suite tests loss from an observed two-follower ensemble, not automatic expansion.

The overlay disables periodic background rebalancing on these three nodes so fault selection remains tied to the observed owner. Ownership handoff and recovery still use actual leases and runtime routing. It does not test the background rebalance policy. Lease expiry waits are eleven seconds for the configured ten-second lease; fault operations and state polling are bounded. Stages have 150-second deadlines and the run has a fifteen-minute deadline. Failed stages remain failures, and later dependent stages remain unexecuted infrastructure errors. There are no automatic test retries or known-bug waivers.

Evidence includes rendered Compose configuration, source/tool provenance, module hashes, HTTP outcomes, ownership epochs, lease ensembles, fleet proofs, recovery logs, lifecycle/network inspections, and disk ownership/emptiness checks. Scoped cleanup unpauses frozen processes and removes only the run's Compose resources. No AWS credentials or resources are used. This is a finite fault schedule, not an exhaustive distributed-system correctness proof.
